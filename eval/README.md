# 评测 harness

一套可复跑的检索/问答评测，用来回答一个问题：**这次改动让系统变好了还是变坏了？**

没有评测，任何检索策略调整（换切分参数、加 rerank、改 top-k）都只能靠"感觉好像好一点"来判断。

---

## 目录说明

| 路径 | 内容 |
|---|---|
| `run_eval.py` | 检索评测主程序（召回 / MRR / 章节多样性 / 延迟） |
| `debug_question.py` | 单题召回诊断：对比 hybrid 与 dense 的 top-k |
| `ab_dedupe.ps1` | 章节级去重的 A/B 对比脚本 |
| `questions/` | 题集：客服 5 题、策划书 12 题、难题 8 题 |
| `results/` | 历史结果存档（JSON，可直接 diff 对比） |
| `agent/` | Agent 工具化的验收与诊断脚本 |
| `ui/` | 界面端到端测试（Streamlit AppTest）与 CSS 回归 |

> **本文档后半部分是「改动记录」，按时间记录了每次改动的问题、做法与实测数据。
> 想了解当前状态，看上面的目录说明 + 下面的「当前基线」即可。**

## 快速开始

在**项目根目录**执行：

```powershell
# 1) 只校验题集（不连服务，改完题目先跑这个）
.venv\Scripts\python.exe eval\run_eval.py --check

# 2) 检索评测（需要 Milvus + embedding API）
.venv\Scripts\python.exe eval\run_eval.py

# 3) 对比纯稠密 vs 混合检索
.venv\Scripts\python.exe eval\run_eval.py --mode dense
.venv\Scripts\python.exe eval\run_eval.py --mode hybrid

# 4) 把召回提到 5 条再测
.venv\Scripts\python.exe eval\run_eval.py --limit 5

# 5) 连生成答案一起评测（额外需要 LLM API）
.venv\Scripts\python.exe eval\run_eval.py --with-answer

# 6) 存档结果，便于和下次对比
.venv\Scripts\python.exe eval\run_eval.py --json eval\results\before.json
```

> 评测前先确认 Milvus 在跑：`Test-NetConnection localhost -Port 19530 -InformationLevel Quiet`

## 指标定义

| 指标 | 含义 | 怎么算 |
|---|---|---|
| **召回命中率** | 正确事实是否出现在送进模型的上下文里 | 该题全部 `expected_facts` 都出现在召回内容的并集中，记 1 次命中 |
| **MRR** | 第一个"完全命中"的片段排在第几名的倒数 | 排第 1 → 1.0，排第 3 → 0.333，没命中 → 0 |
| **P50 / P95 延迟** | 单题检索耗时 | 只计检索，不含生成 |
| **章节多样性** | top-k 覆盖了多少个不同章节 | 不同章节数 ÷ 召回条数；1.0 表示每条都来自不同章节 |
| **答案命中率** | 生成答案里是否包含全部正确事实 | 仅 `--with-answer` 时统计 |

### 为什么用「事实包含」而不是「片段 ID 匹配」

因为段落的 `section` 命名会随解析器调整而变（改一次 heading 识别，所有 ID 全失效）。事实字符串是**语义锚点**，只要文档没改、答案没变，评测就稳定。

### 归一化

比较前对文本做 NFKC + 去空白处理，所以 `10 人` 与 `10人`、全角 `：` 与半角 `:` 视为相同。这避免了空格和全角符号造成的假阴性。

## 题集

| 题集 | 文件 | 题数 | 语料 |
|---|---|---|---|
| 客服知识库 | `questions/cs-5.json` | 5 | `docs/knowledge.txt` |
| 活动策划书 | `questions/drawing-12.json` | 12 | `data/uploads/87061e12bdcb68f6.docx` |

每题结构：

```json
{
  "id": "cs-01",
  "question": "基础版支持多少个正式成员？",
  "expected_facts": ["10 人", "已激活"],
  "expect_section": "四、成员与权限规则",
  "notes": "为什么出这道题"
}
```

- `expected_facts`：**必须全部出现**才算命中。多于一个事实的题，考查的是"能不能一次召回齐"，比单词匹配更严格。
- `expect_section`：目前只用于诊断输出，不参与打分。
- `notes`：给人看的，说明这题的坑在哪。

### 加新题

1. 在对应 JSON 的 `questions` 数组里追加一条
2. 跑 `--check`，它会检查每个 `expected_facts` 是否**真的出现在原文里**——写错一个字都会被抓出来
3. 跑一次完整评测

---

## `--check` 为什么重要

它会读取题集声明的语料原文，逐条核对 `expected_facts` 是否存在。

如果某个事实在原文里根本找不到，评测会**永远判错**——而且看起来像是"检索能力不行"，实际是题目写错了。这类假阴性极难排查，所以在写题阶段就拦掉。

## 当前基线（2026-10-22 实测）

语料：`knowledge.txt` + 策划书 docx。limit=3。

### 基础题集（回归保护）

| 题集 | 模式 | 召回 | MRR | P50 | P95 |
|---|---|---|---|---|---|
| cs-5 + drawing-12（17 题） | hybrid | **17/17** | 1.000 | 99.4ms | 131.0ms |
| cs-5 + drawing-12（17 题） | dense | **17/17** | 1.000 | 99.1ms | 109.3ms |

> ⚠️ **两份基础题集已饱和**（两种模式都满分）。它们现在只能当**回归护栏**用——防止改动把本来能答对的搞坏，但**测不出改进**。

### 难题集（区分度来源）

| 模式 | 召回 | MRR | 章节多样性 | P50 |
|---|---|---|---|---|
| hybrid | 8/8 | **0.938** | **0.71** | 98.9ms |
| dense | 8/8 | 0.917 | **0.75** | 97.7ms |

命中率同样饱和，但 **MRR 与章节多样性仍有区分度**，是当前做 A/B 对比主要看的两项。

### 改动记录 1：章节级去重（2026-10-23）

**问题**：检索按**小块**算相似度，同一章节的多个小块会一起排到前面。实测
「哪些套餐不支持 OCR」的 top-3 **全部来自「二、套餐说明」**。而下游
`build_user_prompt` 送进模型的是 `parent_text`（整章节全文）并按章节去重——
那第 2、3 名送进去的内容与第 1 名完全相同，白白占掉本该给其他章节的名额。

**改法**：在 `milvus.search()` 里把召回粒度从「小块级 top-k」对齐成
「章节级 top-k」——先去重、每个章节只留排名最高的一块，再截取 top-k。
候选池相应放大（`SECTION_DEDUPE_FETCH_FACTOR`）。

**A/B 实测**（`eval/ab_dedupe.ps1`，`RAG_SECTION_DEDUPE=0` 关闭去重）：

| 题集 | 模式 | 章节多样性 | 召回 | MRR | P50 |
|---|---|---|---|---|---|
| 基础 17 题 | hybrid | 0.75 → **1.00** | 17/17 → 17/17 | 1.000 → 1.000 | 104.7 → 100.2ms |
| 基础 17 题 | dense | 0.44 → **1.00** | 17/17 → 17/17 | 1.000 → 1.000 | 93.6 → 99.0ms |
| 难题 8 题 | hybrid | 0.71 → **1.00** | 8/8 → 8/8 | 0.938 → 0.938 | 105.3 → 97.0ms |
| 难题 8 题 | dense | 0.43 → **1.00** | 8/8 → 8/8 | 0.917 → 0.917 | 98.4 → 101.6ms |

**结论**：多样性拉满到 1.00（3 条结果来自 3 个不同章节），召回、MRR、延迟**均无回归**。

**诚实的边界**：由于召回率本来就已饱和（100%），这次改动**在命中率上测不出收益**。
它的价值体现在**上下文覆盖面**——送进模型的章节数从约 1.3~2.1 个变成 3 个。
要验证"更多章节是否带来更好的答案"，需要补 LLM 参与的打分（`--with-answer`）
或更多横跨多节的问题。

**开关**：`RAG_SECTION_DEDUPE=0` 可关闭以复现改动前行为（A/B 对比用）。

> 顺带发现：**dense 的多样性（0.43）远低于 hybrid（0.71）**——纯向量检索更容易
> 把同一章节的多个小块一起召回。去重后两者都到 1.00。

## 改动记录 2：Agent 工具化（2026-10-23，Day 1）

### 做了什么

固定管道是「无论问什么都先检索一次、且只检索一次」——问「知识库里有哪些文档」
它也会去做向量检索。现在把能力包装成 4 个工具交给模型自己选：

| 工具 | 何时用 |
|---|---|
| `search_knowledge` | 知识库相关问题 |
| `list_documents` | 问「有哪些文档」 |
| `summarize_document` | 要求总结某份文档 |
| `web_search` | 知识库没有、且需要外部信息 |

代码：`app/services/tools.py`（工具）、`app/services/agent.py`（构造 Agent）。
顺带把 `qa.build_user_prompt` 拆出 `qa.build_context`——工具返回的应该只是资料，
问题本身已经在对话历史里。

### 验收结果（`eval/agent/verify_agent.py`）

| 问题 | 期望工具 | 实际 | 结果 |
|---|---|---|---|
| 基础版支持多少个正式成员？ | search_knowledge | search_knowledge | ✓ |
| 知识库里现在有哪些文档？ | list_documents | list_documents | ✓ |
| 帮我总结一下策划书讲了什么 | summarize_document | summarize_document | ✓ |
| 1+1 等于几？ | 可不调 | 未调用 | ✓ |

**4/4**。第 2 题是这次改动最直观的收益：旧管道会为一个元问题做向量检索。

### ⚠️ 最重要的发现：长系统提示词会让模型退化

调试延迟时发现模型**偶尔把工具调用写成 XML**（`<parameter name="query">...`）
而不是 OpenAI 的 JSON function call，产生一次无效往返 + 重试。

`eval/agent/diag_prompt_length.py` 实测（3 题 × 4 种提示词）：

| 提示词 | 有效调用 | 畸形调用 | 畸形率 |
|---|---|---|---|
| 长段落（约 300 字） | 3 | **2** | **40%** |
| 当前默认（要点式） | 3 | 0 | 0% |
| 极短（约 70 字） | 3 | 0 | 0% |
| 旧提示词（无工具说明） | 3 | 0 | 0% |

**结论：`mimo-v2.6-flash` 在长系统提示词下会退化。** 提示词必须保持精简
（要点列表 + 每个工具一句话），改 `agent.py` 里那段文字前先跑这个脚本。

改成精简版后，首题延迟从 **22352ms 降到 8779ms**。

### 延迟代价（`ench_agent_vs_fixed.py（已随固定管道一并删除）`）

| 问题 | 固定管道 | Agent | 倍数 |
|---|---|---|---|
| 基础版支持多少个正式成员？ | 3030ms | 10985ms | 3.63x |
| 试用版到期后数据会立刻删除吗？ | 6777ms | 17333ms | 2.56x |

**Agent 慢 2.6~3.6 倍**，因为至少多一次模型往返（先决定调不调工具）。
这是真实代价，不是实现问题——除非换成单次调用就能决定工具的更小模型。

### 合并为单一 Agent（同日完成）

双路径只是做 A/B 的临时脚手架。拿到数据后**已删除固定管道**，现在全项目只有
一个带工具的 Agent：

| 改动 | 说明 |
|---|---|
| `app/core/llm.py` | 删掉 `agent`（`tools=[]`），只保留 `model`；模型名改读 `MIMO_MODEL` |
| `app/services/qa.py` | `stream_answer` 直接把问题交给 Agent，不再预检索、不再拼 prompt |
| `app/services/agent.py` | 删掉 `LEGACY_SYSTEM_PROMPT` |
| `app/config.py` | 删掉 `AGENT_MODE` / `AGENT_MAX_STEPS`（已无意义） |
| `app/ui/streamlit_app.py` | 去掉预检索；引用改从检索日志取 |
| `ench_agent_vs_fixed.py（已随固定管道一并删除）` | 删除（固定管道已不存在） |

**关键修复**：合并后工具返回的**资料原文**也会流经 `stream_mode="messages"`，
必须过滤掉 `ToolMessage`，否则界面上会直接出现一大段检索原文。
`stream_answer` 现在只产出 `AIMessageChunk` 的文本。

**引用来源怎么拿**：Agent 自己决定检索几次，所以界面无法预先知道引用。
`tools.search_knowledge` 把原始命中记进 `_SEARCH_LOG`，流式结束后由
`qa.take_search_log()` 取出渲染。

> ⚠️ 这是模块级状态，面向**单用户本地应用**。Streamlit 每个会话独立跑脚本，
> 但模块级变量跨会话共享——要做多用户并发需改成按会话隔离，
> 或改为从工具返回内容里解析引用。

### 改动记录 3：界面显示工具调用状态（2026-10-23）

**问题**：Agent 自己决定要不要检索，界面事先无从得知。点发送后有 3~8 秒静默，
用户不知道是在思考、在检索、还是卡住了。

**改法**：`qa` 增加 `stream_events()`，产出两类事件：

```python
("tool", {"name": "search_knowledge", "phase": "start" | "end"})
("text", str)
```

`stream_answer()` 退化成只取文本的薄封装（旧调用方不受影响）。
界面用 `st.status` + `st.empty` 手动累积文本并逐步重绘——不能用 `st.write_stream`，
因为那期间需要更新状态提示。

**界面表现**：处理中显示「正在检索知识库…」，完成后折叠成一行「检索知识库」，
用户能直接看到 Agent 做了什么。

**端到端验证**：用 Streamlit 官方 `AppTest` 在无头环境真实执行整个应用
（`eval/ui/test_ui_apptest.py`），覆盖：

| 检查项 | 结果 |
|---|---|
| 首次加载无异常 | ✓ |
| 发送消息无异常 | ✓ |
| 状态条渲染出工具名 | ✓ `检索知识库` |
| 回答正文渲染 | ✓ |
| 工具原文未泄漏到界面 | ✓ |

**顺带观察到的行为**：多轮对话中，如果历史里已经有相关问答，Agent 可能
**不重新检索**直接作答（状态条显示「直接回答（未使用工具）」）。
这不一定是缺陷——省一次检索更快；但存在"历史里的旧答案已经过时"的风险。
值得作为多轮场景的评测项。

## 已知局限

1. **语料太小**（67 个片段）。召回率接近饱和后，指标对改动不敏感——这是真实的，不必为了好看去凑大语料。
2. **事实匹配是字符串级的**。答对了但换了说法（"30 天" vs "一个月"）会被判错。所以在写 `expected_facts` 时优先选**数字、专有名词**这类不会换说法的词。
3. **不评测推理质量**。答案是否通顺、有没有幻觉，这套 harness 不管；它只管"正确事实有没有出现"。
4. **题集规模小**（17 题）。单题权重高，随机波动明显；做 A/B 对比时结论要看差值而不是绝对值。

## 建议用法

改检索策略前后各跑一次，用 `--json` 存档，对比：

```powershell
.venv\Scripts\python.exe eval\run_eval.py --json eval\results\01-baseline.json
# ... 改代码 ...
.venv\Scripts\python.exe eval\run_eval.py --json eval\results\02-after.json
```

两次的 `overall` 段直接对比即可。**如果改动没有带来可测量提升，就诚实记录"无显著差异"，而不是强行归因。**
